> **文档状态**：评审闭合（2026-08-13）
> **评审轮次**：3 轮，27 个问题全部解决

## 一、定位

### 1.1 评审目标

本方案评审的核心是 **0 门槛创作链路**——用户通过框选标注，生成一个可以操作第三方应用的 Skill，然后这个 Skill 可以私人使用、工单提交、官方审核、商城上架。

UI 自动化引擎（PageLocator、LocatorCache 等）是这条链路的实现手段，不是评审目标。引擎内部实现详见附录。

### 1.2 核心原则

不追求通用 UI 理解，依赖用户标注的语义地图 + 运行时视觉定位。

### 1.3 解决的三个核心难题

| 难题 | 传统方案 | 本方案 |
|------|---------|--------|
| 坐标脆弱：分辨率/DPI/窗口大小变化导致固定坐标失效 | 静态坐标脚本 | 语义地图 + 运行时 OCR 动态定位 |
| 控件识别：无法判断哪些文字可点击、哪些是静态文本 | UIA 可访问性树（覆盖不全） | 用户框选标注（人教机器） |
| 通用性：Flutter/Electron/游戏等自绘 UI 不暴露原生控件树 | UIA 失效 | OCR 对任何可显示文字的应用都生效 |

### 1.4 平台范围

| 平台 | 支持状态 |
|------|---------|
| Windows | 支持 |
| Linux X11 | 支持 |
| Wayland | 不支持，不做兼容承诺 |

### 1.5 架构边界

UI 自动化需要访问宿主桌面，不能在 Docker/CubeSandbox 内直接完成截图和输入注入。`agent-toolbox` 只负责提出结构化操作意图；实际的截图、OCR、窗口校验和输入注入由 A 层宿主 `UIAutomationBroker` 执行，并统一经过 A3 Consent 与审计。

```text
Skill → agent-toolbox /ui_automation/* → A 层 UIAutomationBroker
  → Consent/权限/目标窗口校验 → 本地 OCR → 输入注入 → 结构化结果
```

截图和 OCR 结果默认只在本地内存中处理，不进入 B/C 层记忆，不写入日志，不随工单上传。用户主动提交工单时，标注截图必须再次单独确认，并在提交前提供预览和删除入口。

## 二、Skill 包格式

### 2.1 包结构

```
wechat-ops/
├── manifest.json          # Skill 清单，声明"这是一个操作微信的 Skill"
├── ui_map.yaml            # 语义地图（用户标注生成的产物）
└── 入口逻辑               # 调用宿主代理暴露的 /ui_automation/* API
```

`ui_map.yaml` 是 Skill 的核心数据，但不是全部。`manifest.json` 声明 Skill 能操作什么应用，Agent 通过 manifest 知道"什么时候该调用它"。Schema 的唯一事实源继续使用现有 `schemas/skill-manifest-v1.json`；`shared/` 只放需要跨层复用的 DTO，不复制第二份 schema。

### 2.2 manifest schema 扩展

新增两个可选字段（向后兼容，现有 Skill 不需要改）：

```json
{
  "type": "skill",
  "name": "wechat-ops",
  "version": "0.1.0",
  "description": "操作微信的私人 UI Skill",
  "market_id": "wechat-ops@0.1.0",
  "trust": "user_installed",
  "capabilities": ["ui_automation", "ocr_engine"],
  "permissions": ["screen_capture", "input_control"],
  "app_target": {
    "name": "微信",
    "platform": "windows",
    "executable": "WeChat.exe"
  }
}
```

`capabilities` 只表达运行依赖，不能授予权限。`screen_capture` 与 `input_control` 是独立权限：前者允许读取屏幕区域，后者允许鼠标/键盘注入；两者均需加入 manifest schema、宿主权限校验和 A3 审计，不能因依赖 `ui_automation` 而隐式获得。

| 改动 | 位置 | 说明 |
|------|------|------|
| 新增 `capabilities` 字段 | `schemas/skill-manifest-v1.json` | 可选字段，声明依赖的 agent-toolbox 能力 |
| 新增 `app_target` 字段 | `schemas/skill-manifest-v1.json` | 可选字段，声明操作目标应用 |
| 新增 UI 权限 | schema + skill manager | `screen_capture` / `input_control` 分离声明，禁止能力声明替代授权 |
| 加载时能力检查 | skill manager | 声明了 capabilities 但 agent-toolbox 未注册对应能力 → **warning**（不阻断加载），提示"该 Skill 依赖 ui_automation 能力，当前未启用" |
| 文档更新 | `docs/SKILL_DEV_GUIDE_v1.0_zh.md` | 补充两个可选字段的说明 |

以上均为待实现改动。当前 schema 使用 `additionalProperties: false`，直接放入这些字段会校验失败；skill manager 当前也没有能力可用性 warning。

## 三、标注工具

### 3.1 归属

OC 内置的官方工具入口，不是独立进程。用户从 OC 设置页的"创建 UI 操作 Skill"入口进入，复用 OC 现有的 pywebview 前端。工具本身是 skill-scaffold 官方工具链的一部分，不单独分发。

### 3.2 用户操作流程

1. 工具截取当前屏幕
2. 用户在截图上框选控件区域
3. 填写 `target_text`（控件的显示文字）
4. 选择 `type`（button / input / link / display / danger）
5. 工具自动生成 `features` / `locate_by` / 跳转关系

### 3.3 "0 门槛"定义

不需要写代码，不需要理解技术概念。用户只需要：
- 看着截图框选"这是按钮"
- 填上按钮上显示的文字
- 选一下按钮类型

`features`、`locate_by`、跳转关系全部由工具自动生成，用户不接触这些概念。

### 3.4 坐标存储

用户标注的 box 转换为**相对于页面整体的百分比区域**（如 `[70%, 85%, 90%, 95%]`），不存绝对坐标。运行时根据当前截图的尺寸等比例缩放该区域，进行 OCR 匹配。

## 四、运行时定位

### 4.1 定位流程

```
Agent 决策"点击某按钮"
  → PageLocator 判断当前页面
      ├─ 缓存有效 → 直接用缓存坐标
      └─ 缓存失效 → 截图 + OCR → 查找目标文字 → 计算中心坐标 → 建立缓存
  → 执行动作（鼠标点击 / 文本注入）
  → PageTransitionDetector 检测页面是否跳转
      ├─ 跳转 → 清空缓存
      └─ 未跳转 → 保留缓存
  → 返回结果给 Agent
```

### 4.2 用户标注 box 的语义

**用户标注的 box 不是点击坐标，而是搜索约束区域。** 点击坐标永远来自 OCR 文字框中心。用户 box 的作用是"告诉引擎在哪个区域里找这个文字"，用来解决多匹配时的歧义。

运行时完整流程：

1. 用户标注时：框选了一个按钮区域（例如宽 80px 高 30px 的"发送"按钮）
2. 工具存储：这个 box 转换为相对于页面整体的百分比区域（如 `[70%, 85%, 90%, 95%]`）
3. 运行时首次定位：OCR 全屏 → 找到"发送"文字 → 判断该文字框中心是否落在用户标注的百分比区域内
   - 是 → 点击 OCR 文字框中心
   - 否 → 在所有 OCR 结果中找落在该区域内的目标文字 → 点击该文字的框中心
4. 缓存：将"发送"文字框的**实际像素坐标中心**存入缓存（缓存的是运行时 OCR 算出的坐标，不是用户标注的 box）
5. 后续缓存命中：直接用缓存坐标点击，不再 OCR

### 4.3 缓存不变量（含轻量验证）

| 状态 | OCR 操作 | 延迟 | 说明 |
|------|---------|------|------|
| 缓存命中 + 验证通过 | 1 次 crop OCR（100×100） | ~80ms | 截取缓存坐标周围 100×100 区域，验证目标文字仍在 |
| 缓存命中 + 验证失败 | 1 次全屏 OCR | ~1-2s | 目标消失或弹窗遮挡 → 缓存失效 |
| 缓存失效 | 1 次全屏 OCR | ~1-2s | 定位 + 页面识别 + 弹窗检测合并 |
| 操作失败 | 1 次全屏 OCR | ~1-2s | 强制全屏 OCR，判断发生了什么 |

#### 缓存命中时的轻量验证流程

```
缓存命中 (cx, cy)
  → mss 截取 [cx-50, cy-50, cx+50, cy+50] 的 100x100 crop
  → rapidocr 对 crop 做识别
  → 检查 OCR 结果中是否包含 target_text
      ├─ 包含且文字框中心在 (cx±15px, cy±15px) → 确认，用 (cx, cy) 点击
      ├─ 包含但中心偏移 >15px → 弹窗遮挡疑似，缓存失效 → 全屏 OCR
      └─ 不包含 → 目标消失，缓存失效 → 全屏 OCR
```

crop OCR 比全屏快一个数量级——100×100 区域文字量少（通常 1-3 个词），rapidocr 在小图上的推理时间 ~50-80ms。

#### 缓存失效触发条件

- 地图声明"点击 X 后跳转到页面 Y" → 点击后缓存清空 → 下一次定位自然触发 OCR
- 地图声明"点击 X 后不跳转" → 缓存保留 → 下一次定位继续 crop 验证
- 操作失败（元素找不到 / OCR 文字框为空）→ 强制 OCR
- 超过缓存有效期（默认 10s）→ 强制 OCR

#### 核心不变量

**缓存命中时做 1 次 crop OCR 验证，每次缓存失效/操作失败时 1 次全屏 OCR。弹窗检测和页面识别不单独触发 OCR，合并进缓存失效或验证失败后的自然 OCR 中。**

## 五、页面识别

### 5.1 features 自动生成

工具自动生成 features，用户不接触此概念。生成策略：

1. OCR 所有已标注页面的截图
2. 对所有页面做集合差：找出"只在当前页面出现，不在其他页面出现"的文字
3. 这些差异文字即为当前页面的 features

### 5.2 单页面首次标注

用户标注第一个页面时，没有其他页面做参照，features 初始化为当前页面所有 OCR 识别到的文字。后续标注新页面时，工具自动对所有已标注页面做集合差，修正所有页面的 features。

### 5.3 命中阈值

60%。页面 features 命中率 ≥ 60% → 判定为当前页面。

### 5.4 全局元素排除

- **自动检测**：用户标注多个页面后，工具对所有页面截图做 OCR，找出在所有页面都出现的文字 → 标记为全局 → 从 features 中排除
- **用户可手动标记**：标注时可标记"这是导航栏/TabBar"
- **单页面标注时**：工具无法自动排除全局元素，features 为当前页面所有文字。这是已知限制，标注更多页面后会自动修正

## 六、安全机制

### 6.1 Consent 粒度

操作序列级（一个意图一次 consent），不是每次点击一次。

例如"发消息给文件传输助手" = 打开聊天 + 输入 + 发送（3 次 UI 操作），一次 consent 授权整个序列。

序列授权必须绑定 `caller_skill_id + app_target + process_id + window_handle + action_digest + expires_at`。执行每一步前重新校验前台窗口仍属于同一目标进程，任何目标窗口变化、动作集合扩大、超时或 danger 升级都会使原授权失效并重新申请 Consent。用户按下紧急停止热键或切回 OC 后，broker 必须在下一次输入注入前协作式中断。

### 6.2 中途中断

操作序列中每次操作后做页面判定。如果页面与预期不符（如意外弹窗、跳转到未知页面）→ 自动暂停，返回错误给 Agent。

### 6.3 danger 分级

| 级别 | 关键词 | 行为 |
|------|--------|------|
| 硬 danger | 删除、清空、注销、卸载、解散、重置、格式化 | 额外 consent |
| 软 caution | 退出、关闭、移除 | 审计日志标记，不额外 consent |

- danger 标记走**关键词自动 + 用户手动确认**双重路径
- 工具根据 target_text 匹配关键词列表自动标记 danger
- 关键词列表可配置（不硬编码）
- 用户可手动升级（普通 → danger）或降级（danger → 普通）
- 用户降级只影响该份私人地图的提示级别；宿主硬 danger 词表是安全下限，不能被 Skill 或用户标注降级绕过

### 6.4 目标窗口硬锁

- 标注开始时记录目标进程和窗口句柄；运行时每步都校验窗口归属、可见性和前台状态
- 禁止仅按窗口标题匹配，避免同名窗口或恶意标题劫持
- OCR 坐标必须转换到目标窗口客户区，禁止把全屏百分比坐标直接用于点击
- 目标窗口移动、缩放、最小化、进程重启或 DPI 上下文变化时立即清空缓存并重新定位
- 输入前和输入后各做一次窗口身份校验，校验失败时不注入任何鼠标或键盘事件

### 6.5 错误处理与 C 链路对接

元素找不到时停止执行，走后置校验链路：

- broker 返回待新增的结构化错误码（如 `E_UI_ELEMENT_NOT_FOUND`），由 PlanOrchestrator 将 step 标为 FAILED
- 下游 step 标 BLOCKED（C-4 传播）
- plan 状态判定为 blocked 或 failed（C-6）
- 用户可手动 retry（C-5），retry 后重新执行 → 成功则解除下游 BLOCKED

这些 UI 错误码当前尚未加入 `shared/error_codes.py`，实现时必须先登记结构化错误元数据，不能只返回自由文本。

### 6.6 审计日志

所有操作记录审计日志，包括：
- 操作类型（click / input / read）
- 目标文字
- 坐标
- 结果（success / failed / blocked）
- danger 级别

审计日志不得记录截图、OCR 全文、剪贴板原文或输入内容；文本字段只记录不可逆摘要或脱敏后的短描述。标注截图与普通运行审计分库存放，并遵循可删除、可追溯原则。

## 七、商城分发

### 7.1 流程

| 阶段 | 流程 |
|------|------|
| 私人使用 | 用户标注 → 生成私人 Skill → 本地直接使用 |
| 工单提交 | 用户觉得地图做得好 → 联网提交工单 → 附带 ui_map.yaml + 标注截图 |
| 官方审核 | 官方验证语义地图的完整性、特征文字的有效性、元素覆盖度 |
| 上架商城 | 审核通过 → 上架 → 其他用户下载 → 适配自己的屏幕即可用 |

### 7.2 跨分辨率/DPI 兼容

核心方案天然兼容 DPI 变化——不存绝对坐标，只存语义描述。缓存是运行时缓存，每次都重新 OCR，所以 DPI 变化不影响定位逻辑，只可能影响 OCR 识别精度。高 DPI 下小字号 OCR 精度问题，需要在验证阶段专门测试。

### 7.3 版本失效检测

运行时如果某个页面的 features 匹配率持续低于阈值（如多次都是 40%），Agent 应主动提示"该应用可能已更新，UI 地图可能过期，建议重新标注或等待更新"。

### 7.4 法律风险

公开分发第三方应用的 UI 结构描述，可能触及厂商 ToS 条款。短期只支持"私人使用"，不公开分发。正式上架到公共商城前需要做 ToS 评估。

## 八、技术依赖

| 依赖 | 用途 | 说明 |
|------|------|------|
| rapidocr_onnxruntime | OCR 文字识别 | 轻量 ONNX 模型，CPU 推理 |
| mss | 截图 | 纯 Python，跨平台，~50ms/次 |
| pynput | 鼠标键盘操作与事件监听 | 纯 Python，轻量 |
| pillow | 图像处理 | 已存在 |

明确不引入：pyautogui（截图和定位功能被 mss + pynput 替代）、opencv（pillow 足够）、任何深度学习框架。

当前基线仅已声明 `onnxruntime`，`pillow` 位于 `desktop` 可选依赖；`rapidocr_onnxruntime`、`mss`、`pynput` 均尚未加入项目依赖。实现时应新增独立的 `ui-automation` optional dependency，避免普通本地聊天安装被强制带入桌面控制依赖。

## 九、测试策略

| 层级 | 覆盖内容 |
|------|---------|
| 单元测试 | PageLocator 的文字匹配逻辑、LocatorCache 的失效逻辑、PageIdentifier 的页面判定逻辑 |
| 集成测试 | 使用 fixture 截图 + 预生成 ui_map.yaml，验证完整执行循环 |
| 端到端测试 | 选择一个真实的轻量应用（如 Notepad），从"标注 → 生成 → Agent 操作"全程验证 |
| 回归测试 | 模拟不同分辨率/DPI 下的 OCR 定位精度 |

### 核心测试用例

1. 文字唯一匹配 → 返回正确坐标
2. 文字多个匹配 → 按百分比区域约束筛选正确的一个
3. 文字无匹配 → 返回 E_UI_ELEMENT_NOT_FOUND，不执行点击
4. 缓存命中 + crop 验证通过 → 不触发全屏 OCR，直接用缓存坐标
5. 缓存命中 + crop 验证失败 → 触发全屏 OCR 重新定位
6. 页面跳转后 → 缓存清空，重新 OCR
7. 弹窗遮挡 → crop 验证检测到目标消失 → 全屏 OCR
8. 文本输入 → 剪贴板粘贴成功，验证输入框内容正确
9. danger 元素点击 → 额外 consent 弹出
10. 操作序列中途中断 → 页面与预期不符 → 自动暂停

### 10.1 实现前置顺序

1. 定义 manifest 扩展、UI 权限与结构化错误码

### 评审过程

### 阻断项决策

**问题**：缓存命中时 0 OCR → 弹窗出现 → 缓存坐标意外落在弹窗的危险按钮上 → 误点击

**决策**：路径 2——缓存命中时做轻量 crop 验证（100×100 区域 OCR，~80ms），不选路径 1（接受风险）。

**理由**：danger 关键词检测防的是"已知危险按钮被 Agent 主动点击"，防不住"缓存坐标意外落在弹窗的危险按钮上"。crop 验证能以 80ms 代价拦住弹窗遮挡误点击。

### 非阻断项决策

1. **danger 关键词分两级**：硬 danger（额外 consent）+ 软 caution（审计日志标记），"关闭"/"退出"降级为 caution
2. **manifest capabilities 加载时 warning**：声明了但能力不可用 → warning 不阻断加载
3. **文档拆两份**：链路设计（主文档）+ 引擎技术设计（附录）
